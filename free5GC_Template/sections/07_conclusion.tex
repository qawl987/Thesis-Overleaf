\section{Conclusion and Future Work}
\label{sec:conclusion}

This paper presented an intent-driven orchestration system for 5G RAN and core network slices using free5GC, OCUDU, Kubernetes, and Nephio. The E2E orchestrator translates service expectations into aligned core and RAN parameters, while the OCUDU and free5GC Operators provide the RAN NSSMF and Core NSSMF/VNFM reconciliation paths. Dynamic core subscriber state is injected through a complementary free5GC-facing interface. Experiments show the intended eMBB/URLLC traffic differentiation, while the measured operator stage confirms that domain reconciliation is not the dominant source of the approximately 30-second management latency; GitOps synchronization is.

Several limitations remain. The prototype demonstrates a control pattern rather than a production-ready slice-management platform. It focuses on two representative service classes, eMBB and URLLC; a production system would need a richer service catalog, tenant quotas, authentication and authorization policies, and explicit admission rules.

The evaluation uses emulated UEs and a virtualized Kubernetes environment, so the throughput results should be read as configuration-effect evidence rather than a production capacity benchmark. CPU scheduling, virtual networking, and buffering can influence loss, jitter, and throughput; the main evidence is relative: when the generated slice configuration changes, traffic allocation changes in the expected direction.

Future work should add 3GPP Release 18 and Release 19 style intent features, including feasibility checks, conflict reports, negotiation, and utility functions. The hybrid southbound design should also migrate more subscriber state into declarative resources so that RAN and core changes can share package lifecycle, audit trail, and rollback behavior. On the data plane, deeper integration with Linux traffic control, UPF-level QoS enforcement, or additional OCUDU scheduling hooks could improve differentiation beyond RAN scheduling alone; on the management plane, reducing GitOps synchronization latency or adding policy-controlled fast paths would broaden operational applicability.
